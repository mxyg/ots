# Ops Tool Spec (OTS) · 核心规范 v0.1

> **草案，不稳定。** 跟着一个真实实现一起写的，不是委员会文件。v1.0 之前会有破坏性改动。
>
> ★ [英文版](core.md)是正本。两版有出入时以英文为准。

## 0. 范围与分层

本规范定义运维类软件**该向 AI 暴露什么**，以及**结果与权限长什么样**。
它**不定义**传输和发现——那是 MCP 的事。

```
   AI（Claude 或别的）
        │
   MCP  │  ← 传输、发现、调用。已有标准，不归我们管。
        │
   ── Ops Tool Spec ──  ← 有哪些工具、返回什么、谁能调
        │
   你的运维软件
```

实现方**可以**用普通 HTTP 而不是 MCP（或者两个都提供）来暴露同一套工具。
下面的规则说的是工具本身，两种方式都适用。

## 1. 工具返回判定，不返回人话

工具的返回**必须**是结构化的值，**不得**是写给人看的句子。

```jsonc
// 错 —— AI 得去解析人话，而且只有一种语言能用
{ "note": "IPv4 正常（IPv6 没有可用地址），网段 192.168.1.0/24" }

// 对
{ "verdict": "v4-only", "networks": ["192.168.1.0/24"], "usb": "lan" }
```

**判定（verdict）** = 一个命名某种**状态**的稳定字符串码 + 得出它所依据的数值。
码用小写加连字符，且在实现的各个版本之间保持稳定。

这一条能同时买到三样东西，所以它排第一：

- **AI 不用解析人话。** 省 token，不会读错。
- **软件能翻译。** 用字符串拼接出来的句子**锁死了语序**，语序不同的语言根本没法翻进去。
- **共享词汇表才成为可能。** 判定码是本规范里**不同厂商真正能达成一致**的那部分。

给人看的文字由**客户端**产生——界面按用户的语言渲染那个码，或者由 AI 自己组织说法。
实现方**可以**额外给一个渲染好的句子字段，供日志和命令行使用；
客户端**不得**依赖它。

### 1.1 判定码

与传输、领域无关的**核心码**在本文档定义。领域规范定义自己的码；
码是扁平字符串，**不做命名空间**，领域规范自己负责不撞车。

实现方遇到自己没有对应码的状态时，**不得**临时编一句人话，
而应返回 `unknown` 并附上手里已有的证据。

## 2. 只读工具与改系统工具是两类

每个工具**必须**声明自己属于哪一类：

| 类别 | 含义 |
|---|---|
| `read` | 只观察。除了实现自己的缓存和日志，什么都不改。 |
| `mutate` | 会改某台机器上的状态——本机、远端设备、或者网络。 |

**发流量算只读**（ping、端口探测、取流探测都是 `read`）。
改路由表、改防火墙规则、改地址、装软件是 `mutate`。

实现方**必须**能在完全禁用 `mutate` 的情况下，只提供 `read` 那一套。

## 3. 授权只能来自人，不能来自调用

`mutate` 工具在执行前**必须**通过实现方自己的界面，**针对这一次具体操作**取得人的同意。
确认提示**必须**说清楚要改什么。

**声称已获授权的参数一概不算数。** 实现方在决定要不要执行改动时，
**必须**忽略 `user_approved`、`confirmed`、`force`、`emergency`
这类字段，以及任何「用户已经批准了」的自由文本。

实现方**不应**提供「信任这个 AI，以后不用问」这种设置。
确认的价值就在于**人看到了那个具体的改动**，一刀切的豁免恰恰把这个价值毁掉了。

改动**应当**在执行前先持久化登记、执行后可回退，
这样「已批准」和「已完成」之间崩溃了，状态还能恢复。

## 4. 必须假设调用方可能已被污染

驱动运维软件的 AI 会读设备 banner、日志文件、抓到的包、HTTP 响应、别人写的配置。
**这些东西里任何一样都可能含有针对 AI 的文字。**
一个行为端正的 AI 是**可以被说服**去请求一个有害改动的。

所以实现方**不得**把 AI 当作权威来源。
**这才是第 3 条的理由**——不是出于谨慎，而是一种具体的、已被充分认识的攻击。

实现方**应当**默认只监听回环地址。监听可路由地址**应当**要求显式配置并设置令牌。

## 5. 与软件自身界面对等

每个工具**必须**对应界面上人也能做、也看得见做过的事。

只能通过 API 触达的能力就是一个后门：
它绕过了界面提供的确认、警告和操作记录，而且**盯着这个软件看的人根本不知道它发生过**。

满足这条最省事的办法：**让界面自己也成为同一套 API 的客户端**。

## 6. 长任务

扫描、抓包、持续监测塞不进一次请求-响应。
这类工具**必须**立即返回一个任务号，实现方**必须**提供查进度、取中间结果、取消的工具。

工具**不得**把一次调用挂在那里等任务跑完。

## 7. 错误

失败**必须**报成带稳定 `code` 的结构化错误，不得报成判定，也不得报成人话。

**错误的含义是「工具没能得出答案」**——它和「工具成功地判断出某个东西坏了」是两回事，
后者是判定。

核心错误码：

| 码 | 含义 |
|---|---|
| `invalid-argument` | 请求本身不合法或超范围 |
| `not-supported` | 请求合法，但本平台或本构建不支持 |
| `permission-required` | 需要实现方目前没有的权限 |
| `approval-required` | 改动正等待人工确认（见第 3 条） |
| `approval-denied` | 人拒绝了 |
| `unreachable` | 目标连不上 |
| `timeout` | 超时未完成 |
| `internal` | 实现自己的缺陷 |

能事先知道需要权限的，**应当**在**动手之前**就返回 `permission-required`，
好让 AI 能告诉用户需要什么，而不是失败之后才报。

## 8. 版本与符合性

实现方声明自己对齐的规范版本。在 `0.x` 阶段，任何小版本都可能有破坏性改动。

两档符合性：

- **只读符合**——实现第 1、2、5、6、7 条，且只暴露 `read` 工具。
- **完全符合**——另外对自己的 `mutate` 工具实现第 3、4 条。

**暴露了改系统工具却没实现第 3、4 条的，不符合本规范**，
且**不得**声称符合任何一档。
