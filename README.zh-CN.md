# Ops Tool Spec (OTS) · 运维工具规范

**一套让 AI 能安全驱动运维类软件的词汇表。**

> 状态：**v0.1 草案，不稳定。** 会有破坏性改动。欢迎试用并告诉我们哪里写错了。
>
> ★ 英文版 [README.md](README.md) 是正本；本文是中文译本。

## 名字

简称 **OTS**，全称 **Ops Tool Spec**（运维工具规范）。三个词，和
MCP（Model Context Protocol）、LSP（Language Server Protocol）、DAP（Debug Adapter Protocol）同构。

★ **名字刻意不带厂商。** ONVIF 不叫「Axis ONVIF」，MCP 不叫「Anthropic MCP」——
**一个以某家公司命名的规范，它的竞争对手不会采纳**，
而采纳与否是一份规范唯一值得被写出来的理由。署名写在 README 和 NOTICE 里，那才是它该在的地方。

（曾考虑 **OATS**，否掉了：撞 FINRA 的 Order Audit Trail System，
同在「技术+合规」语境里；而且 oats 是燕麦，**搜索结果会被燕麦片淹没**——
可搜索性对一份想被全世界采纳的规范是硬指标。）

## 要解决什么

[MCP](https://modelcontextprotocol.io) 已经把**「软件怎么把工具暴露给 AI」**这件事定下来了——
传输、发现、调用。那一层已经有标准，本规范**建立在它之上，不和它竞争**。

MCP 刻意没管的是：**某一类软件到底该暴露哪些工具**。

- 一个网络诊断软件该提供哪些工具，分别叫什么
- 工具该返回什么，才能让 AI 不用去解析人话就能判断
- 哪些操作 AI 可以自己做，哪些必须人点头
- AI 读到的数据本身可能带着指令时，怎么才不出事

今天每家的答案都不一样。结果就是：一个 AI 会用甲家的工具，换到乙家还得重新教一遍。
别的领域早就用「通用传输 + 领域语义层」解决了——摄像机有 ONVIF（跑在 HTTP/SOAP 上），
医疗记录有 FHIR（跑在 HTTP 上）。**AI 可调用的运维软件，这一层目前还是空的。**

## 五条规则，一句话版

1. **工具返回判定，不返回句子。** 判定 = 一个稳定的码 + 相关数值。人话由客户端按用户的语言渲染。
2. **只读和改系统分成两类。** 只读的随便调；改系统的动的是别人的机器，受第 3 条管。
3. **授权只能来自人的动作，不能来自调用参数。** 请求里写 `"user_approved": true` 一律无效。
4. **必须假设调用方可能已被污染。** 设备 banner、日志、抓包内容、网页——AI 读到的东西都可能
   夹带针对 AI 的指令。**这才是「改系统必须人点头」的真正理由**，不是出于谨慎。
5. **不许有只存在于 API 的能力。** AI 能做的，人在软件界面上也能做、也看得见。

详见 `spec/v0.1/core.md`。

## 我们为什么写它

我们做运维类软件——安防、核销、播控，还有一套网络工具箱——
上面那些问题我们反复回答了好几遍，每次答得还不太一样。
这份文档就是把那些答案写下来一次，公开，**让任何人都能实现，包括竞争对手**。
这一点正是它是「规范」而不是「产品功能」的原因。

参考实现是 **NetKit** 网络工具箱。它的由来是 2026-09-19 那天，
一位工程师为了查一个现场，手工折腾了一整天——改网卡地址、扫端口、探 RTSP 流、
SSH 进去看 GPU 占用——**这里面每一步本来都该是 AI 可以直接调的一个工具**。
